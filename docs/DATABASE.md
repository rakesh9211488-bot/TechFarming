# Database setup and migrations

The versioned SQL files under `Database/migrations/` create account, session, device, telemetry and jobs tables used by the active API. The older SQL examples remain available for historical context; they are not the setup procedure.

## 1. Preserve an existing database

Do not run the initial migrations against a database that already contains application tables without reviewing it. Back up existing schemas using your normal MySQL backup process and verify the dump before changing anything.

For a local backup in PowerShell, with `mysqldump` available:

```powershell
New-Item -ItemType Directory -Force D:\TechFarming-backups
mysqldump -u root -p --databases user_db job --result-file="D:\TechFarming-backups\before-migrations.sql"
```

Enter the password at the prompt, not in the command. Substitute your existing schema names. Use a new backup filename for each run to preserve earlier backups. Do not commit dumps or real account records.

## 2. Create isolated development schemas

Using an administrative MySQL session, create new schemas. This avoids modifying an older application database:

```sql
CREATE DATABASE techfarming_users_dev CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE DATABASE techfarming_jobs_dev CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Create a dedicated local MySQL user through your administrative tool with a strong password. Grant it SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER and REFERENCES on these two schemas only. CREATE, ALTER and REFERENCES are needed for the reviewed migrations and foreign keys. Do not use the administrative account in the application configuration.

The migration command deliberately does not create databases, accounts or permissions.

## 3. Set Server/.env

Copy `Server/.env.example` to `Server/.env` if needed. Supply your dedicated user's credentials and use:

```dotenv
DB_USERS_DATABASE=techfarming_users_dev
DB_JOBS_DATABASE=techfarming_jobs_dev
```

Keep this file private. The two schema names must differ. Check that an existing process environment variable is not overriding the file.

## 4. Review the plan

From a PowerShell terminal at the repository root:

```powershell
cd Server
node scripts/migrate.js --plan
```

This prints file names and checksums without connecting to MySQL or changing data. Read those SQL files before applying them.

## 5. Apply the migrations

After installing backend dependencies with `npm ci`:

```powershell
node scripts/migrate.js
```

The runner creates a `techfarming_migrations` tracking table in each schema and takes a MySQL advisory lock to prevent concurrent runs through this runner. Each successful migration is recorded with its checksum. Running it again skips unchanged successful migrations.

The initial migrations use CREATE TABLE without IF NOT EXISTS for application tables: an existing conflicting table causes failure rather than being silently accepted or overwritten. No sample accounts or real personal data are inserted.

## 6. Check the results

In MySQL, inspect each schema:

```sql
SHOW TABLES FROM techfarming_users_dev;
SHOW TABLES FROM techfarming_jobs_dev;
SELECT name, status FROM techfarming_users_dev.techfarming_migrations;
SELECT name, status FROM techfarming_jobs_dev.techfarming_migrations;
```

Expected tables: `user_sign_up`, `seller_sign_up`, `user_sessions`, `user_devices`, `device_readings` and `jods_list`. The seller table preserves the historical schema but seller signup is not active. The jobs table retains the original spelling for compatibility. Account email uniqueness is enforced; passwords must be hashes generated by the application, never manually inserted plaintext.

## Recovery and future changes

MySQL DDL commits implicitly. These migrations cannot promise transactional rollback. If a run fails after a tracking row is marked `started`, the runner refuses to retry that migration automatically. Inspect the schema and tracking row, recover from a verified backup or reconcile the incomplete change, and only then update the tracking state with an administrator. Do not delete tracking rows blindly.

Do not edit an applied migration. Add a new numbered migration for later schema changes. Checksums detect edits to tracked SQL; they do not prove that a live schema has not been changed manually.

This establishes the active account, session, device, telemetry and jobs schema. Commerce and rover/image integrations remain separate work. The older product/order example SQL is not an implemented commerce schema.
